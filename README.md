# mytfctl

`mytfctl` — small interactive CLI for managing Terraform input
for the local libvirt/KVM infrastructure project.

The application does not replace Terraform.

Its purpose is to:

1. collect host parameters interactively;
2. validate user input;
3. generate `terraform.tfvars`;
4. run `terraform fmt`;
5. run `terraform validate`;
6. run `terraform plan`;
7. generate a small Ansible inventory snippet.

`terraform apply` is intentionally not executed by `mytfctl`.
The final infrastructure change remains as explicit user action.

## Current workflow

```text
mytfctl
  |
  +-- VM naming
  |
  +-- host name
  +-- IPv4 address
  +-- memory
  +-- vCPU
  |
  +-- terraform.tfvars
  |
  +-- terraform fmt
  +-- terraform validate
  +-- terraform plan
  |
  +-- Ansible inventory snippet
  |
  `-- terraform apply <- manual
```
  
## Host input

Each host has:

- hostname
- IPv4 address
- memory in MiB
- vCPU count

Defaults:

- memory: 2048 MiB
- vCPU: 2

Example:
```text
Hostname: worker01
IPv4 address: 192.168.100.21
Memory MiB [2048]:
vCPU [2]:
```

## VM naming

VM names are generated from:
```text
<prefix>-<hostname>-<suffix>
```
Defaults:
```text
prefix = lab
suffix = ubuntu
```
For example:
```text
lab-worker01-ubuntu
lab-worker02-ubuntu
lab-cp01-ubuntu
```
The prefix and suffix are configurable when mytfctl starts.

## Terraform

Terraform remains responsible for:

- libvirt resources;
- qcow2 overlays;
- cloud-init;
- VM hardware configuration;
- networking;
- resource lifecycle;
- state;
- planning and applying infrastructure changes.

`mytfctl` only prepares Terraform input and runs the non-destructive
Terraform workflow up to `plan`.

Ansible inventory

After a successful plan, `mytfctl` generates:
```text
ansible-inventory-snippet.yml
```
Example:
```text
worker01:
  ansible_host: 192.168.100.21
worker02:
  ansible_host: 192.168.100.22
cp01:
  ansible_host: 192.168.100.11
```
The application intentionally does not modify the user's complete
Ansible inventory.

The generated fragment can be copied into an existing inventory.

## Files

The main Terraform files have the following roles:
```text
mytfctl/
├── cloud-init/
│   ├── network-config.yaml.tftpl
│   └── user-data.yaml.tftpl
├── mytfctl.py
├── .gitignore
├── locals.tf
├── main.tf
├── README.md
├── variables.tf
├── versions.tf
└── terraform.tfvars
```
Terraform configuration
`versions.tf` — Terraform and provider requirements. This file is currently maintained manually.
`variables.tf` — input variables accepted by the Terraform configuration.
`terraform.tfvars` — concrete values for the current infrastructure. This file is generated by mytfctl and is not committed to Git.
`locals.tf` — derived values calculated from the input variables, such as libvirt VM names.
`main.tf` — the actual infrastructure resources managed by Terraform.
`cloud-init/` — templates used to generate the cloud-init seed for each VM.

For each host defined in `terraform.tfvars`, Terraform creates three main resources:

`qcow2 volume` — a VM disk created as an overlay using the common Ubuntu golden image as its backing store.
`cloud-init ISO` — a seed image containing the initial user configuration and network configuration for the VM.
`libvirt domain` — the virtual machine itself, including its CPU, memory, disks, network interface, display and other virtual hardware.

Generated files

The following files are generated locally and should not be committed:
```text
.terraform/
terraform.tfstate
terraform.tfstate.backup
terraform.tfvars
ansible-inventory-snippet.yml
```
`.terraform/` — local Terraform working directory containing downloaded providers and other local data.
`terraform.tfstate` — Terraform state describing the infrastructure managed by the current configuration.
`terraform.tfstate.backup` — backup of the previous Terraform state.
`terraform.tfvars` — generated input values for the current run.
`ansible-inventory-snippet.yml` — generated YAML fragment containing Ansible host mappings.

The Terraform dependency lock file, `.terraform.lock.hcl`, is not generated data that should be ignored. It is committed to Git so that Terraform provider versions and checksums remain reproducible across machines.
